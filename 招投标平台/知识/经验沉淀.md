## E1 多智能体流程需要一个「中枢产物」

**结论**：多个 Agent 协作时，要有一个贯穿全程的结构化产物（台账/矩阵/清单），各 Agent **读写它**，而不是互相直连传全文。

**为什么**：没有中枢，各阶段的产出物会各玩各的（解读出维度报告、规划出目录树），交界处必然丢失信息。有中枢，每一步都在同一条主线上累加，天然可追溯。

**反例**：让 Agent A 的输出全文塞进 Agent B 的提示词——信息量爆炸、无法增量更新、出错无法定位。

**通用度**：★★★★★　**来源**：`note.md`#写标（响应矩阵）

---

## E2 协调者应是「信息枢纽」，不是「中央指挥官」

**结论**：串联多 Agent 的角色，只在**异常处理**和**跨阶段确认**时介入；日常流转交给 Agent 自主完成。

**为什么**：中央指挥官会成为吞吐瓶颈，每一步都过一遍协调者，性能优势完全消失。

**风险提示**：这是**最容易在实现时做歪**的一条——一旦图省事让协调官管日常流转，架构就退化成串行。

**通用度**：★★★★★　**来源**：`note.md`#写标

---

## E3 多租户 AI 知识库必须做命名空间级隔离

**结论**：知识库隔离要做到**每个租户独立 Collection**（L2），**metadata 过滤不够**。

**为什么**：metadata 过滤是查询时的软隔离，一旦过滤条件写漏或 prompt 注入绕过，数据就串了。在强合规场景下，串数据的后果不是「体验差」，而是**违规**（如串通投标认定）。

**通用度**：★★★★☆（凡多租户 + 强合规场景皆适用）　**来源**：`note.md`#写标（企业知识库）

## E4 不可逆动作前用快照固化

**结论**：凡不可撤销的操作（开标、发布、结算），执行瞬间把**当时的事实**固化成不可变快照。

**为什么**：事后原始数据仍会变动，没有快照就无法复现「当时到底发生了什么」，争议时无法举证。

**通用度**：★★★★★　**来源**：`note.md`#交易平台（开标固化投标名单与文件清单）

---

## E5 状态推进优先用惰性计算，而非定时任务

**结论**：仅有「时间到了就该变」的单一规则时，在**读取时**计算状态，不要引入调度器。

**为什么**：省掉一个后台组件、一套失败重试、一个运维面。行为对用户等价。

**边界**：需要**主动通知**（发邮件、推站内信）时，惰性不成立，必须回到定时任务。

**通用度**：★★★★☆　**来源**：`docs/02-状态机.md`#惰性推进

## E6 生成类流程要在高成本步骤前插人工闸门

**结论**：`解析 → 【人工确认大纲】 → 生成正文`，而不是一口气生成到底。

**为什么**：这是 5 家竞品的**共同做法**（确认大纲、确认全局事实、选模板）。解析可能出错，若直接生成正文，错误会被放大数倍，返工成本远高于一次确认。

**附加做法**：把跨章节的一致性约束（项目名、工期、地点）抽成**「全局事实」单点确认**，改它则清空下游缓存——保证全文一致。

**通用度**：★★★★★　**来源**：`note.md`#竞品（喜鹊、易标）

---

## E7 长任务必须可续跑

**结论**：多步长任务每步落盘，支持 checkpoint 恢复。

**为什么**：生成一份长文档可能耗时数十分钟，中途失败若要从头再来，成本不可接受。

**通用度**：★★★★★　**来源**：`note.md`#竞品（易标「长任务 checkpoint 可恢复」）

## E8 按「要求行」组织比按「章节」组织更可追溯

**结论**：当上游给出一份要求清单时，用**要求清单的行**作为主键组织产物，每条要求记录响应内容、证据、责任人、状态；而不是按输出文档的章节树组织。

**为什么**：章节树只能回答「我写了什么」，要求行能回答「**每条要求我回应了没有**」。后者才是交付验收的依据。

**通用度**：★★★★☆（凡「输入清单 → 输出文档」的映射任务皆适用）　**来源**：`note.md`#写标、#竞品对照

## E9 脚手架模板 README 必须当天替换

**结论**：`create-next-app` / `vite` / `django-admin` 生成的 README 是模板垃圾，**建项目当天就替换掉**。

**证据（本项目实证）**：`apps/web/README.md` 至今仍是 `create-next-app` 原始模板，讲的是怎么部署到 Vercel；而真实的启动方式在 `README.md`、`docs/04-演示脚本.md`、`apps/web/package.json` 三处**互相矛盾**（见 `知识/项目现状.md` → 待人工同步）。

**为什么**：`README` 是半年后唯一的入口。模板 README 比没有 README 更糟——它给出了**看似权威的错误答案**。

**通用度**：★★★★★　**来源**：本项目直接观察

## E10 记录「被否决的方案」，否则半年后会重新讨论同一个问题

**结论**：决策记录里必须写**否掉了什么、为什么否**，而不只写最终选了什么。

**为什么**：只记结论，后人（包括三个月后的自己）看到现状时会想「为什么不用更简单的方案 X」，然后重新论证一遍——而这个论证早就做过了。

**本库实践**：`知识/决策记录.md` 每条含「被否决」字段。

**通用度**：★★★★★　**来源**：本次建库设计
